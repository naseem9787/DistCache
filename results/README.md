# results/

Raw output of every benchmark session run for Phase 6, kept so that every number in the README
can be traced to the measurements it came from. Each directory holds `raw.jsonl` (one JSON line
per measured run: command lines, load-generator result, server `INFO`, per-thread CPU) and
`env.json` (machine, kernel, compiler, build flags, binary hashes, health probe where recorded).
`report-*` directories hold the rendered reports (`report.md`, `charts/*.svg`) generated by
`bench/harness/report.py`.

All sessions ran on the same machine (see the README for the hardware). **Sessions are not
interchangeable**: absolute numbers for persistent configurations moved between sessions
(page-cache write speed and `fsync` latency of the virtual disk both changed by large factors).
Compare configurations *within* a session; the harness interleaves binaries for that reason.

| directory | what it is | session state |
|---|---|---|
| `run-a`, `report-a` | first full suite, Phase 5 behaviour only | normal |
| `run-b`, `run-c`, `report-b`, `report` | full suite twice, final binary vs Phase 5 baseline interleaved; `report` pools B and C | normal |
| `ladder`, `report-ladder` | optimization ladder, first attempt | **degraded** (RSS 90-230 MiB vs ~35-100 normal; page-cache writes 187 MB/s vs 4 GB/s). Kept, not used for conclusions |
| `ladder2`, `report-ladder2` | optimization ladder, 8 interleaved repeats per binary | healthy (health probe passed) |
| `ab-stripes`, `report-ab-stripes` | striped log buffer vs single buffer (design rejected) | normal |
| `ab-spin`, `ab-spin2`, `ab-spin3` and reports | `std::mutex` vs spin lock on the log buffer; `ab-spin3` has 12 repeats and is the one quoted | normal |
| `w1-a`, `w1-b`, `report-w1a`, `report-w1b` | WAL overhead attribution with the diagnostics build (no persistence / log to tmpfs / log with data discarded / log to disk) | normal |
| `prof`, `prof2`, `prof3`, `prof4` | sampling-profiler sessions (the 4 W1 variants, 1 run each). `prof3` is clean. `prof2` passed the health probe and `prof4` was flagged narrowly at its start, and in both every variant, including no persistence, ran 2-4x slower than in `prof3` (and the real-disk variant also showed ~1.6 s `write()` stalls); they are quoted only as what they are, see README §6.3. `prof` was taken with an older diagnostics binary and is not used | `prof3` normal; `prof2`, `prof4` slow host |
| `recovery` | recovery times, first attempt | likely degraded (wide ranges), kept, not used |
| `recovery2`, `report-*` | recovery times, 5 repeats | healthy |
| `equiv`, `report-equiv` | `build/distcache_baseline` vs a pure Phase 5 build (`scripts/build_baseline.sh`): equivalent within noise | healthy |
| `always-d`, `report-always-d` | same-session `fsync always`, final vs Phase 5 build | healthy |
| `ring` | `bench_ring` output (balance, movement, cost of the consistent hash ring; Phase 7) | n/a (deterministic except timings) |
| `cluster` | Phase 7 scale-out (1-3 nodes x direct / smart client / router x pipeline 1, 16, 64) and rebalance (add a node with and without migration), 5 repeats | healthy at the start; the probe drifted slower during the session (CRC 34 -> 40 ns, tmpfs 5.2 -> 2.6 GB/s) |
| `cluster-check` | node-1 vs router-1 at pipeline 16, 8 repeats | **degraded** (CRC 65 ns at the end, CV 32-36 %): kept, only the direction is quoted |

The profiler dumps (`results/prof*/profiles/*.txt`, 2-3 MB each, raw addresses) are not
committed; the symbolized summaries are in `docs/benchmarks/phase6/profiles/`.
